# QA Round 6: db-security (tenant isolation and database security)

Covered: every table/view/function/trigger/policy/grant in public, private, cron, net, vault, storage, realtime, extensions on live project `ydihurtbcnoflhormgzi` (catalog queries), both advisors, PostgREST exposure with the public anon key (read-only GETs), and rolled-back two-synthetic-user probes. NOT covered: Edge Functions, auth.* config (JWT expiry, MFA settings, redirect URLs), storage object contents (no buckets exist), and the Next.js API routes except where they consume a DB object.

Method notes: all write probes ran inside one `DO` block that ends in `RAISE EXCEPTION`, so nothing persisted (re-checked: 0 leftover `qa6-*` users, 0 leftover rows). No real user data was read or printed.

| DBS-3 | P2 | `src/app/api/auth/password/change/route.ts:60-66` (revokes other sessions, rotates trusted device, never touches `sms_ingest_tokens`); `sms_ingest_tokens.token` plaintext, non-expiring | Persistence after session theft. Password change / "sign out others" does not rotate or deactivate it, so the attacker keeps an authenticated SMS-ingest channel (can inject fake SMS that become expenses/income, pair/learn templates) after the user has secured the account. Column SELECT by owner adds nothing beyond the API but the token is stored unhashed. | Static: grep for `ingest` in the password route = 0 hits; policy list shows `sms_ingest_tokens_select_own`; column grant includes `token`. | On password change and global sign-out set `is_active=false` for all the user's tokens (device re-arms via setup-token); long term store a hash and show the token once; revoke column SELECT of `token` from `authenticated`. | Static |
| DBS-4 | P2 | `public.remember_merchant_category_on_edit` (SECURITY DEFINER trigger on expenses UPDATE) | Global cross-tenant integrity and a privacy leak. Two accounts (sybils are cheap, anonymous sign-in is enabled) that each own an `sms_parse_log` row (created by posting SMS with their own ingest token) and set the same category on an expense with that `sms_log_id` get `merchant_categories` flipped for ALL users (`source='user'`, `where source <> 'seed'`). `sample_merchant` is copied from the raw expense description and `merchant_categories` is SELECTable by `anon` (verified live: anon GET returned rows incl. `sample_merchant`). Live data now: 4 `user` rows, 0 PII-shaped, votes from 1 distinct user, so not yet abused. | Static + live anon GET `/rest/v1/merchant_categories`. fp-check: needs ≥2 voters and a real parse-log row; attacker-controlled both; rated P2 not P1 because category poisoning only mis-labels. | Require ≥3 distinct accounts with account age, rate-limit per user, never copy free-text description (store only normalised key), restrict anon SELECT to `merchant_key,category`. | Static |
| DBS-5 | P3 | `public.biometric_devices` column grant (`secret_hash` SELECT for `authenticated`) | Secret-bearing column owner-selectable. `trusted_devices` was locked down in 0236 (table-level SELECT revoked, probe P14e = permission denied) but `biometric_devices.secret_hash` still has `authenticated` column SELECT. fp-check: value is a hash of a random device secret (`newDeviceSecret`), a hash alone does not let a stolen session impersonate the device; it is a hardening gap, not an escalation. | Column privilege query; policy `own biometric device read`. | `REVOKE SELECT (secret_hash) ON public.biometric_devices FROM authenticated`. | Confirmed (grant), exploit refuted |
| DBS-6 | P3 | live DB: schema `net` | pg_net hardening. `anon` and `authenticated` have USAGE on schema `net`, EXECUTE on `net.http_get/http_post/http_delete`, and ALL on `net.http_request_queue` and `net._http_response` (RLS off; 6 response rows). If `net` were ever added to PostgREST's exposed schemas this is open SSRF plus response disclosure. fp-check: PostgREST currently exposes only `public, graphql_public` (anon probe `Accept-Profile: net` = PGRST106), and these are Supabase defaults, so unreachable today. | anon curl with `Accept-Profile` for net/private/cron/vault/storage/auth = 406 each. | `REVOKE USAGE ON SCHEMA net FROM anon, authenticated` (cron/vault already have no USAGE). | Confirmed (grants), exploit refuted |
| DBS-7 | P3 | `private.two_factor_gate`, `platform_settings.enforce_2fa_gate` | 2FA gate is observe-only and fail-open. Live config is `mode=report` limited to one user id, so no request is ever blocked; `second_factor_status` and the gate are therefore not a control yet. The first block of `two_factor_gate` also has `exception when others then return`, i.e. even in `enforce` mode a malformed claim or settings read error skips the gate (the second block correctly re-raises only in enforce mode). `guard_two_factor_flag` only protects the flag when mode<>off. | Function source and live `platform_settings` row. | Before switching to enforce: fail closed in the first block (or log and raise when mode=enforce). | Confirmed (config), Static (fail-open) |
| DBS-8 | P3 | project auth settings | Advisor `auth_leaked_password_protection` WARN: HIBP check disabled. | `get_advisors security`. | Enable in Auth settings. | Confirmed |
| DBS-9 | P3 | default privileges `public`/postgres | `ALTER DEFAULT PRIVILEGES` grants EXECUTE on every new function to `anon, authenticated, service_role` (and supabase_admin defaults grant anon rwd on tables). Every function created without an explicit `REVOKE` is instantly an RPC. Today every other `public`/`private` DEFINER function beyond the 11 intended is revoked (verified by `has_function_privilege`), so this is a discipline risk, not a live hole (DBS-1 shows the same class: a DEFINER RPC that was intentionally granted but under-checked). | `pg_default_acl`. | `ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE EXECUTE ON FUNCTIONS FROM anon, authenticated, PUBLIC;` and add a CI check on `has_function_privilege`. | Confirmed |
| DBS-10 | P3 | `site_leads`, `site_stats` | `authenticated` holds table SELECT on a PII table (site_leads) with RLS enabled and no policy. Advisor triage (security): `rls_enabled_no_policy` x47 INFO = intentional deny-all service-only tables (checked each list entry against grants: none writable by anon/authenticated except as above); `authenticated_security_definer_function_executable` x11 WARN = the 11 intended RPCs (analysis below: 8 ownership-asserting, 3 vulnerable = DBS-1, `analytics_touch`/`second_factor_status` are `auth.uid()`-bound); `auth_allow_anonymous_sign_ins` x~40 WARN = false positive for authenticated-role policies (they fire because anonymous sign-ins also use role `authenticated`; every policy is bound to `auth.uid()`; `cron.job`/`job_run_details` policies are `username = CURRENT_USER`, so anon/authenticated see 0 rows); `auth_leaked_password_protection` = DBS-8. Performance advisor: 47 `unused_index` INFO only (no unindexed FK, no multiple-permissive-policy, no auth_rls_initplan warnings). Not actioned: dropping unused indexes right after launch is a judgement call.
