# QA Round 5: API and security (prefix API)

Covered: all 96 `src/app/api/**/route.ts` (matrix below), `proxy.ts`, `lib/server/{cronAuth,rateLimit,clientGate,nativeApiCors,publicApiRateLimit,admin/{guard,session,sso,stepUp,credentials}}`, `lib/supabase/resolveRouteUser.ts`, `lib/sms/{resolveSmsUser,deviceGate}`, `lib/server/devices/registry.ts`, vercel.json vs pg_cron jobs (read-only SQL). Not covered: bodies of `sms/parse` (1.6k lines, only auth/validation/limits read), `admin/emails`, `admin/plans`, `admin/platform`, `admin/loyalty`, `admin/crashes`, `admin/ai/cost`, `admin/users/[id]/financial|export|activity` (guard + permission mapping confirmed, handler bodies skimmed or not read), RLS policies, real network/e2e.

## Findings

| ID | P | file:line | finding | evidence | suggested fix | status |
|---|---|---|---|---|---|---|
| API-1 | P1 | `api/sms/setup-token/route.ts:75-109` | `DELETE` (rotate) takes the client-supplied `X-Buddget-Device-Id` and mints a new active ingest token for it with none of the checks `GET` has (`isRevokedDevice`, `isUnregisteredDevice`). A phone the owner removed (still holding a valid session) can mint a fresh SMS ingest token and keep posting SMS. It also deactivates tokens first and ignores that update's error, so a failed insert leaves the user with no token | `repro/api/devices.test.ts.txt` API-1: GET with revoked device = 403 (control); DELETE with the same header = 200 + new token (expected 403) | copy the revoked/unregistered guards from GET into DELETE; insert the new token before deactivating the old, check both errors | Confirmed |
| API-2 | P1 | `api/push/register/route.ts:55,64-82` | The revoked-phone check runs only `if (deviceId)` from the BODY. A removed phone omits `deviceId` (or any other device) and its token is upserted into `push_tokens` again, so it hears every push. The same "drop the id" bypass `smsDeviceGate` was written to close for SMS. Any client-chosen new `deviceId` also creates a fresh un-revoked `user_devices` row (no cap), so removal is only as strong as the phone's honesty | `devices.test.ts.txt` API-2: with deviceId in body 403 (control); body without it but header = removed device: 200 and a `push_tokens` row (expected 403, no row) | read the id from `X-Buddget-Device-Id` too and run `isRevokedDevice`/`hasAnyDevice` exactly like `smsDeviceGate`; cap devices per account | Confirmed |
| API-3 | P1 | `api/devices/[id]/route.ts:58-69` | Removing a phone writes `revoked_at` FIRST, then deletes its SMS tokens, push tokens, biometric binding and trusted-device row. If any cleanup call errors the route answers 500, but a retry finds no un-revoked row and answers 404, so the cleanup can never be finished from the app: the removed phone keeps its biometric secret (`biometric/signin` does self-heal on next use) and a trusted-device row that skips 2-step | `devices.test.ts.txt` API-3: cleanup update fails, first call 500, retry 404 (expected 200), biometric row still present | do the cleanup first or make the route idempotent (run cleanup for an already-revoked device instead of 404); wrap in one RPC | Confirmed |
| API-4 | P2 | `api/biometric/register/route.ts:15-48` | Creating a biometric binding needs only a valid session (`resolveRouteUser`), no recent sign-in. Anyone holding a session for a moment (stolen token, unlocked phone) can bind a device id and secret of their choosing; `biometric/signin` then mints fresh sessions for the account indefinitely, bypassing password and 2-step, until the owner changes the password (`password/change` clears bindings) or removes the device. `secret_hash` is any client string of 32+ chars; a non-hex or short-hash binding can never sign in | static: compare `two-factor` (disable needs `verifyReauth`) and `account/delete` (amr within 5 min); register has neither | require `signedInWithin(amr, ...)` or `verifyReauth` on POST; validate `secret_hash` as 64 hex chars | Static |
| API-5 | P2 | `api/auth/password/change/route.ts:32-54` | Two linked defects. (a) The route deletes ALL biometric bindings and trusted devices BEFORE `updateUserById`. If the update is refused (same password, weak-password policy, Auth outage) the user is told it failed but has already lost biometric login and 2-step trust on every phone. (b) The "same password" branch tests `/same/i` in the Auth message; GoTrue's message is "New password should be different from the old password." (code `same_password`), so the branch never fires: the reset/change screens get a generic 500 instead of `errorSamePassword`, and (a) has already run | `repro/api/passwordChange.test.ts.txt`: Auth error with GoTrue's message gives 500 (expected 422) and `delete` ran on `biometric_devices` and `trusted_devices` | test `error.code === 'same_password'`; delete bindings only after the update succeeds, or restore on failure (keep the revoke-others ordering the comment explains) | Confirmed (mock uses GoTrue's documented message) |
| API-6 | P3 | `lib/supabase/resolveRouteUser.ts:104-115`, all `resolveApiUserId` routes | Most routes (SMS, AI, notifications, devices, support, flags, entitlements) trust a locally verified JWT, so a user suspended in the portal (`ban_duration`) or removed from a device keeps API and AI-quota access until the access token expires (about 1 h). `resolveVerifiedIdentity` exists for this and is used only on destructive routes. Accepted trade-off by the code comment, but device removal (API-2/3) and suspension are the cases it matters for | static | use the verified path on `sms/*` and `push/*`, or revoke the removed phone's refresh token (`auth.admin.signOut`) in `devices/[id]` DELETE | Static |
| API-7 | P3 | `api/devices/route.ts:54-60`, `registry.ts upsertSelf` | `POST /api/devices` creates a `user_devices` row for any header-supplied id (<= 100 chars, no pattern) with no per-account cap or rate limit; `GET /api/devices` returns them all. A client bug or script can bloat the table and the Devices sheet | static | cap at e.g. 20 live devices; reuse `DEVICE_ID_PATTERN` | Static |
| API-8 | P3 | `api/sms/confirm/route.ts:65-77` | Claim is a bulk `update ... where sms_hash = X` followed by `maybeSingle()`. The unique index is `(user_id, sms_hash) WHERE is_duplicate = false`, so a duplicate-flagged twin with the same hash and `awaiting_confirmation=true` is also updated; `maybeSingle()` then errors on 2 rows, `row` is null and the route answers 404 after BOTH rows left the confirmation queue. Needs a twin that stays awaiting; not reproduced against the real DB | static | claim by `logId` only, or add `.eq('is_duplicate', false)` | Static |
| API-9 | P3 | `api/auth/device/check/route.ts:22-52`, `lib/auth/resolveDeviceId.ts:14-17` | 2-step trust is "the device id header matches a `trusted_devices` row". The header wins over the HttpOnly cookie and is plain text on every request, so the id is a bearer secret that is sent, logged by clients and unrelated to the session. Anyone who learns one trusted id for the account (it is a UUID) skips the second factor with a password-only session | static | bind trust to a server-set secret (cookie / keychain) and compare a hash, as biometric does | Static |
| API-10 | P3 | `api/site/event/route.ts:7-17` | The only rate limit on this public write is a per-isolate `Map`; on serverless that is no limit (every cold instance restarts it), and the key is the first `x-forwarded-for` hop. A script can inflate `site_stat_bump` counters. Also `proxy.ts` and `biometric/signin`, `check-email`, `feedback` pick the first XFF hop while `health/deep` documents that hop as client-supplied; harmless behind Vercel (which overwrites it) but inconsistent | static | use `isRateLimited(service, 'site-event:'+ip, ...)` like `site/lead`; one shared `clientIp()` | Static |
| API-11 | P3 | `api/admin/auth/password/route.ts:18-24` | Changing the admin password does not check `isLocked(cred)` nor call `recordFailure` on a wrong guess, so it is throttled (10 per 15 min) but never feeds the 5-strike lockout that login and step-up use | static | mirror `stepUp` | Static |
| API-12 | P3 | `api/feedback/route.ts:44-58,66` | `user.email` can be null (JWT claim), producing "Submitted by: null"; `fetch` and `res.json()` are unguarded, so a Linear timeout is an unhandled 500 after the hourly quota was already consumed | static | handle null email; try/catch around the Linear call, count the hit only on success | Static |
| API-13 | P3 | `vercel.json`, `api/cron/month-carry/route.ts` | `month-carry` is intentionally unscheduled (file header: writes live money). Known open item from Goals v3; listed so the matrix is complete. No other route is orphaned: pg_cron job 15 (POST) and all six Vercel crons (GET) match exported methods | SQL `cron.job`: one API caller (job 15, 55 s timeout); route exports | none until sign-off | Static |

Checked and found sound (no finding): all seven cron routes and the three webhooks compare secrets/signatures with `timingSafeEqual` and reject when the secret is unset; every `admin/*` route goes through `guardAdmin` (staff, CSRF header on writes, unlocked session, per-op permission, step-up on destructive ops, rank checks on role changes); `account/delete` needs a verified identity with a sign-in from the last 5 min and is rate limited; no route reads a user id from the body except `push/send`, which forces it to equal the caller; no unvalidated redirects; no stack traces in responses (the three `details: flatten()` bodies expose only schema field errors); `support/*`, `notifications`, `devices/[id]` PATCH filter every query by the caller's id; `/api/prices/refresh` is public but atomically debounced to one crawl per hour.
